The repository root at that checkpoint contains no Tauri application manifest, frontend source, or `src-tauri/` implementation, so these slices begin from a greenfield application scaffold rather than modifying an existing runtime architecture.

# Assumptions

## Verified

1. **This is a pre-implementation checkpoint.** There is no existing Tauri architecture to preserve or migrate at the target commit.
2. **There must be exactly three serial reviewed slices.** Parallelization is neither required nor advisable for the overlapping scaffold, Cargo, Tauri state, and command surfaces.
3. **`CapturePipeline` is the sole product-level platform extension seam.** Parser, persistence, and Tauri IPC should not be absorbed into its public contract.
4. **All three screenshot artifacts must come from one buffered pre-event frame.** A two-phase “raw event now, screenshots later from a newer frame” design would violate ADR 0001.
5. **The bundle is not product-UI-affecting.** The frontend is only a bare development trigger; there is no design acceptance gate in this bundle.

# Architecture

## Owning seams

| Seam                                       | Responsibility                                                                                                                                                                                                         | Must not own                                                                         |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **Tauri command facade**                   | Deserialize command arguments, call the application services, translate errors, retain the supplied channel for the active recording.                                                                                  | Capture threads, filesystem layout logic, title rules, or permission API calls.      |
| **Recording coordinator**                  | Sole owner of `Idle → Starting → Recording → Stopping/Failed → Idle`; enforces one active recording, composes permissions, capture, parser, store, and channel, and emits one terminal outcome.                        | Direct Core Graphics, ScreenCaptureKit, or AX calls.                                 |
| **`CapturePipeline` trait**                | Product-level platform boundary. Starts and stops capture and produces ordered, portable capture packets containing raw facts, resolved metadata, frame age, and one encoded screenshot triple.                        | Tauri IPC, workflow folders, JSONL, workflow manifests, or user-facing step parsing. |
| **macOS `CapturePipeline` implementation** | Event tap, per-display streams, immutable frame snapshots, click/focus resolution, crop geometry, PNG encoding, queueing, stream/tap health, and display-reconfiguration handling.                                     | Workflow schema or channel payload policy.                                           |
| **Permission module**                      | Ordered status and request operations for Input Monitoring, Accessibility, and Screen Recording. A narrow private source abstraction permits deterministic tests without becoming a second product platform interface. | Recording state or capture startup.                                                  |
| **Domain core**                            | Exact schema-v1 types, `KeySemantics`, title formatting, and one-event-to-one-step parsing. It remains macOS- and Tauri-free.                                                                                          | Filesystem operations or native API flags.                                           |
| **`WorkflowStore`**                        | Every filesystem mutation: folder creation, shot-file writes, JSONL append, manifest replacement, loading, and listing.                                                                                                | Image capture or PNG encoding.                                                       |
| **Live channel adapter**                   | Publish committed parser output and one terminal error/status envelope.                                                                                                                                                | Durability or backpressure control for capture.                                      |

This separation follows DEC-001’s single capture platform boundary, DEC-002’s independent store, and DEC-003/004’s parser and classifier ownership.

### Important correction to the existing PR-02 plan

The current PR-02 plan says the store “only records shot paths given to it,” while AC-003 says **all persistence goes through `WorkflowStore`** and requires the PNGs to exist at those paths. Letting `src-tauri/src/capture/` write shot files directly would create an untested second persistence path and violate the stated owning seam.

The compatible interpretation of the accepted trait names is:

* Capture encodes or supplies the three PNG payloads.
* `WorkflowStore::append_event` is the per-event persistence operation and accepts the event plus its screenshot triple.
* The JSON implementation writes the shot files and appends the event line.
* PR-02 tests this using small valid PNG fixtures; it does not need real macOS frames.

That retains the accepted `append_event` method name without adding another public storage method.

## Start flow

1. The coordinator atomically claims the `Starting` state. It should not hold a Tauri-managed mutex while performing permission checks, waiting for streams, or writing files.
2. The permission module checks Input Monitoring first. Accessibility is not touched until the ordering condition is satisfied; Screen Recording may be checked independently. `start_recording` fails before folder or native capture startup unless all three are granted.
3. The store creates the readable per-workflow folder and `shots/`. The candidate design also creates a valid empty v1 manifest so failed or interrupted work remains discoverable.
4. The macOS pipeline starts all active-display streams and waits for one usable frame from each before enabling the event tap. Enabling the tap last avoids accepting events for which no pre-event frame exists.
5. Only after the pipeline is live does the coordinator publish the workflow ID and transition to `Recording`.

If stream warming or tap startup fails, the coordinator performs one failed-start cleanup/finalization path and returns to `Idle`.

## Per-event flow and commit invariant

The event pipeline should have one externally meaningful completion point:

```text
input observed
  → pre-event frame-set snapshot retained
  → window/element metadata resolved
  → one-frame screenshot triple derived and encoded
  → screenshots and JSONL line committed through WorkflowStore
  → one step parsed and added to the in-memory manifest
  → one live step emitted
```

More precisely:

1. The ListenOnly tap callback records only lightweight facts: event kind, coordinates or key code, modifier flags, wall-clock timestamp, monotonic timestamp, and a cheap immutable handle to the current per-display frame set. It must not perform AX lookups, PNG encoding, filesystem I/O, Tauri IPC, or wait on a full queue. Dedicated-CFRunLoop ownership is accepted architecture.
2. A bounded FIFO worker resolves the window and element:

   * Click: point-based window lookup and AX hit test; fallback crop centered on the click.
   * Key-down: frontmost app’s focused window and system focused element; fallback crop centered within the focused window.
3. The selected frame lease is the only source for full, window, and element PNGs. The worker validates and clips point-space rectangles before applying the display’s scale.
4. The pure parser may run once the event metadata is complete. It routes key title behavior through `KeySemantics`.
5. `WorkflowStore::append_event` writes the three shot files first, then appends and flushes one complete JSON line. If JSONL append fails, orphan shots are preferable to a durable event that references missing files.
6. After the store reports success, the coordinator appends the step to its in-memory manifest and emits exactly one step payload. This establishes the invariant that every visible live step has a durable raw event and complete shot triple.

AC-004 describes parser output as the capture-channel boundary, so the later committed contract should be treated as **step delivery**, despite the earlier issue #7 resolution referring to event delivery.

## Stop and fail-stop flow

Normal stop should be serialized through the same coordinator:

1. Transition to `Stopping`; disable the tap so no new jobs enter.
2. Close the producer side of the queue.
3. Drain already accepted jobs in FIFO order.
4. Stop streams and join the tap/run-loop thread. Queued jobs must retain any frame data they need independently of live streams.
5. Atomically replace `workflow.json` using a same-directory temporary file and rename.
6. Close the channel with a terminal status and clear the active session.
7. Return the workflow ID.

Fail-stop should use the same terminal path but capture the first error reason. Multiple near-simultaneous failures—tap disabled, stream failure, store failure, or permission loss—must result in one state transition and one surfaced terminal error, not competing stop routines. DEC-007 requires retaining already committed JSONL and shots and explicitly rejects automatic recovery UX.

Whether fail-stop drains jobs that already hold valid frames should remain an implementation choice bounded by safety: never continue accepting events, never publish a step whose persistence failed, and never block finalization indefinitely.

## Concurrency boundaries

### Event tap thread

The tap owns its CFRunLoop thread for its entire lifetime. Its callback performs constant-bounded work and uses nonblocking queue submission. Runtime `CGEventTapIsEnabled` checking belongs to this owner or an associated health timer.

### Screen-stream callbacks

Each stream callback should only publish a newer immutable frame lease into the frame broker. It should not perform per-event crops or write files. A capture event snapshots the frame-set handle at event time; reading “whatever frame is latest” later in the worker would reintroduce the post-event race that ADR 0001 rejects.

The selected crate’s frame lifetime and `Send`/`Sync` properties require proof. Preferred order:

1. Retain a safely reference-counted native frame/texture if supported.
2. Otherwise copy to an owned immutable pixel buffer at the stream boundary.
3. Do not introduce an unsafe cross-thread wrapper merely to preserve the planned shape without first proving the underlying native ownership contract.

### Ordered capture worker

A single worker is the pragmatic initial design because JSONL order, channel order, and in-memory step order remain naturally identical. Parallel event encoding would require sequence numbers plus an ordered commit buffer and would increase retained-frame memory. Parallelism should only be added in response to measured failure of the actual gate.

### Queue saturation

A bounded queue cannot simultaneously guarantee all three properties under arbitrary load:

* never block the event-tap callback,
* never drop an event,
* never exceed the memory bound.

The current decisions do not choose which invariant yields on saturation. Silent loss is the worst option because AC-001 would look superficially healthy while violating per-event capture. The recommended default is immediate fail-stop with an explicit “capture overloaded” error and recorded queue depth. This requires a decision or at least an explicit plan invariant; it should not remain accidental channel-library behavior.

### Display reconfiguration

The frame broker should replace display sets atomically only after replacement streams have produced usable frames. Existing frame leases remain valid for already queued events. An event targeting a new or changed display before a usable frame exists should trigger explicit fail-stop rather than using an unrelated display or a post-event on-demand capture. The accepted scope requires stream restart on display changes, but the current acceptance criteria do not prove it.

## Persistence and compatibility

### Schema-v1 obligations

PR-02 should pin the exact JSON shape with golden fixtures, not merely round-trip arbitrary Rust types. The referenced schema resolution includes:

* event `id`, timestamp, kind, display ID, nullable click/key fields;
* window, element, shots, and capture metadata;
* relative `shots/...` paths;
* manifest `schema_version: 1`;
* steps with `event_ids` arrays;
* no persisted `KeySemantics` verdict.

### Atomicity

For each event:

1. Write each PNG to a temporary file under `shots/`.
2. Rename all three into their final names.
3. Serialize exactly one compact JSON object followed by `\n`.
4. Append and flush that line.

The filesystem cannot atomically commit three PNGs and one JSONL line as a single transaction. “Shots first, log second” chooses harmless orphan files over broken durable references. A load operation should ignore unreferenced files.

For manifests, temporary-file plus rename is sufficient. A full migration or journal system is unnecessary within the budget.

### Migration policy

There is no legacy application data at the checkpoint, so PR-02 should not build a generic migration framework. It should:

* accept schema version 1;
* return an explicit unsupported-version error for any other version;
* retain `event_ids` as arrays from day one;
* avoid persisting policy-derived classifier output;
* keep paths relative so workflow folders remain movable;
* tolerate additive unknown JSON fields where Serde’s normal behavior permits it.

The manifest provides the schema version for its associated JSONL file. A future breaking event change should therefore also change the manifest version; an additive event field can remain compatible if older readers may ignore it.

### Signing compatibility

The fixed bundle ID and actual proven-gate signature are hard requirements because TCC grants depend on stable identity.

The personal certificate should preferably be injected through the local build environment rather than committed as an unconditional requirement for every clone. The gate must inspect the built `.app` and confirm that it is signed by the accepted identity. The specification root should verify that this injection mechanism still leaves the project buildable with standard Tauri commands on machines without that certificate; otherwise DEC-006 and the cloneable-build deliverable are operationally in tension.

# Conflicts and planning corrections

## 1. Screenshot persistence ownership

**Conflict:** PR-02 says the store only records paths; AC-003 says all persistence is through the store.

**Correction:** Define `append_event` as the compound shot-plus-event persistence operation and prove it with fixture PNGs in PR-02.

## 2. PR-03 is not a reviewable first integration point

The current PR-03 combines:

* event tap and CFRunLoop lifetime;
* multiple ScreenCaptureKit streams;
* frame buffering;
* multi-display geometry;
* two AX resolution paths;
* PNG encoding and queue behavior;
* permission gating;
* single-session state;
* store integration;
* channel delivery;
* commands;
* frontend trigger;
* real acceptance.

That is a complete subsystem, not the smallest practical review slice. It also says there is no unresolved implementation work while acknowledging an unverified AX API shape and depending on continuous-stream behavior that the cited research did not directly prove.

**Correction:** PR-02 should already prove orchestration against a deterministic fake pipeline. PR-03 then reviews native behavior rather than discovering domain/lifecycle behavior at the same time.

## 3. Permission status shape is underspecified

AC-005 requires reporting all three permissions while prohibiting any Accessibility call before Input Monitoring has been requested. A three-boolean response may be incapable of representing “Accessibility deliberately not checked yet.”

**Correction:** Verify the native Input Monitoring status API first. The command return type may need an explicit state such as `granted`, `denied`, `not_requested`, or `blocked_by_prerequisite`, rather than booleans. This is an API-shape decision, not frontend design.

## 4. Older research recommendations are superseded

Issue #3’s on-demand `SCScreenshotManager` recommendation is incompatible with ADR 0001. The committed ADR and DEC-001 win; the research remains useful only for ScreenCaptureKit availability, scaling, and deprecation facts.

## 5. Channel payload terminology differs across records

Issue #7 says the channel streams captured events. DEC-003 and AC-004 later establish that each event is parsed immediately and that parser output is the channel payload boundary.

**Correction:** Stream a typed envelope whose data item is the parsed step, including its `event_ids`; keep raw events on disk.

## 6. The current PR-03 flow does not pin durability before visibility

The written flow mentions channel delivery before store append. Even if that ordering was not intended as normative, the implementation plan should explicitly choose persistence-before-channel to avoid phantom live steps.

## 7. Manual capture is a high-cost verification mechanism

PR-03 marks “new high-cost verification mechanism: none,” but the real signed two-app gate requires TCC setup, native and Chromium applications, focused/unfocused typing, and disk inspection. It should be treated as a first-class merge gate with a scripted receipt, not an informal smoke check.

   * live channel item count and order equal manifest step count and order;
   * `capture.frame_age_ms` values are present and nonnegative;
   * the signed identity and bundle ID are correct.

The receipt should state the apps and versions used, focused/unfocused cases, event count, shot count, workflow folder, and any measured maximum queue depth.

### UI/live-data gate

No design acceptance. The development page only needs start/stop controls and enough live output—such as the latest title and received count—to prove that the channel is working. Product permission and review UX remain in the next capability.

### Non-goals

No review UI, step editing, rename/delete/reveal commands, grouping, app hotkeys, shortcut-specific badges, automatic recovery UI, SQLite, or non-macOS backend.

# Risks and missing evidence

## Critical

### 1. Frame ownership may invalidate the planned threading model

The accepted design needs a cheap pre-event frame snapshot, but the selected Rust wrapper’s native frame types may not be safely movable or retainable across the stream callback and capture worker. Copying every continuous frame into owned memory may be correct but expensive; unsafe cross-thread movement is not an acceptable default. This must be resolved before implementing the full pipeline.

### 2. Bounded queue overload has no accepted semantic

The specification requires a bounded queue and a triple for every key-down, while the tap callback must remain nonblocking. Normal typing may generate full-screen PNG work faster than one worker can complete it. Queue capacity is not a substitute for an overload policy.

Recommended candidate: **fail-stop immediately and visibly on saturation; never silently drop or coalesce.**

### 3. Permission ordering may require a richer command contract

The implementation must verify what production API state is available before finalizing the command response schema. Calling AX merely to obtain a boolean can violate AC-005 on first launch.

### 4. Current storage plan permits persistence to escape the store

Unless corrected, PR-03 will likely write PNGs itself while PR-02 only appends JSONL. That breaks the declared store seam, weakens SQLite replaceability, and makes AC-003’s failure cases difficult to test.

### 5. The final slice is too large for the budget as currently written

The repository has no scaffold at the checkpoint, yet PR-03 currently includes all native APIs, orchestration, persistence integration, channel integration, command lifecycle, and real proof. Moving platform-independent orchestration to PR-02 is the main architectural mitigation.

## High

* **Coordinate conversion:** global point coordinates, display-relative frame coordinates, Retina scale, negative display origins, spanning windows, and key-down display selection must be isolated as pure geometry and tested.
* **Display-change events:** accepted behavior exists, but no acceptance criterion covers restart correctness. A state-level test plus a minimal manual hot-plug check is needed if available.
* **Fail-stop races:** tap, stream, permission, encoder, store, and user stop can race. Only one owner may finalize.
* **Crash semantics:** “append-only and crash-safe” does not define `flush` versus `fsync`, process crash before final manifest, or partial-event handling. The plan should promise process-level consistency, not unsupported power-loss durability.
* **Signing portability:** a hardcoded personal identity can conflict with standard clone/build expectations.
* **Chromium fallback determinism:** Chromium may return a coarse AX container rather than an AX error. The resolver needs a deterministic “implausible frame” rule, such as zero-sized, outside the window, or effectively the whole web area.

## Medium

* Exact modifier set and display ordering for multi-modifier titles.
* Exact key-code-to-name behavior for non-printable keys and keyboard layouts.
* Whether `name` is optional at start or represented by an empty/default value.
* Active-workflow `get_workflow` behavior.
* Channel-disconnect behavior: capture continuation versus fail-stop.
* README ownership. PR-01 creates a minimal README, but PR-03 should update it with actual completed scope, removed scope, window-crop caveat, macOS limitation, measured tradeoffs, and the proven-gate result. The broader AI-usage and final walkthrough obligations may be completed at project closure.

# Recommendation

Adopt the three serial slices with one boundary correction:

1. **PR-01:** signed scaffold and ordered permission API.
2. **PR-02:** schema, `KeySemantics`, parser, complete `WorkflowStore`, `CapturePipeline` trait, recording coordinator, fake pipeline, lifecycle and live-channel integration.
3. **PR-03:** real macOS adapter, bounded capture queue, geometry, native health/failure behavior, dev trigger, and AC-001 proof.

Before implementation, the specification root should pin four architectural invariants in the slice plans:

* A capture packet represents one event and one screenshot triple derived from one retained pre-event frame.
* `WorkflowStore::append_event` owns shot-file persistence as well as the JSONL append.
* A step is published only after its event and all three shots commit.
* Queue saturation has an explicit, tested behavior.

## Rejected alternatives

* **Keep the current PR boundaries unchanged:** rejected because PR-03 becomes the first point where lifecycle, persistence, channel, native APIs, and failure semantics meet.
* **Create a fourth native spike PR:** technically attractive but contradicts the accepted three-PR delivery constraint.
* **Move raw capture into PR-01:** rejected because it destroys the scaffold/permission cohesion and still cannot prove the final screenshot/store/channel path.
* **Let capture code write `shots/` directly:** rejected because it violates AC-003’s owning seam.
* **Use an unbounded queue:** rejected because each queued full-screen frame can retain substantial memory and the decision explicitly calls for a bound.
* **Silently drop on queue full:** rejected because it violates literal per-event capture and can pass superficial UI checks.
* **Block the tap callback:** rejected because it risks timeout-driven tap disablement.
* **Emit live steps before persistence:** rejected because it creates visible steps with no durable workflow representation.
* **Add a generalized migration framework now:** rejected because there is no prior application schema and the budget only requires an explicit v1 guard.
* **Build product permission/review UI in PR-03:** rejected by DEC-005 and the bundle non-goals.

## Consequential unresolved question

**What happens when the bounded screenshot queue fills?**

The recommended candidate is **fail-stop with one explicit overload error, preserving all events and shots already committed**. That is consistent with the nonblocking tap and existing fail-stop posture, but queue saturation is not named in DEC-007. Because the alternative materially changes recording completeness, resource use, and user-visible failure behavior, the spec-work root should record this policy rather than allowing the queue implementation to decide it accidentally.
