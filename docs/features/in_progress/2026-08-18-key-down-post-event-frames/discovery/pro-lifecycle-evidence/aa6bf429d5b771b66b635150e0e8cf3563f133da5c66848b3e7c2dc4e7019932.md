# Primary research disposition

All required paths were available at commit `cb938b4b2166ffb90c659ad42bf0c70f6fe60deb`; no local-only evidence was supplied.

**The worker-side bounded wait is the correct owning seam.** It is the only existing point where key-down metadata has been resolved, the DEC-008 display can be selected, FIFO event ordering remains structural, and the tap callback stays nonblocking.

The current PR-01 plan should **not** be implemented unchanged. It needs five material corrections:

1. A post-event frame must be bounded by both sides of the accepted timing window: `event_ts < frame.ts_ns <= deadline_ts`. As written, the proposed broker query has no upper bound, so a worker arriving late could select a frame from after the 250 ms deadline instead of using the pinned fallback.
2. Pipeline shutdown must keep SCStreams alive until the worker has drained accepted jobs. The current implementation stops streams before joining the worker, which prevents a waiting key-down from receiving its post-event frame during normal stop.
3. Injecting only `now()` is insufficient for deterministic active-wait tests. The sleep/wakeup behavior and timing constants must also be test-controlled.
4. Event-anchored deadlines prevent **stacked** 250 ms waits, but they do not make queue saturation impossible. At the minimum queue capacity of four, five further events while the first job is waiting are enough to reject the next event.
5. Post-event frames from a changed display generation can have geometry inconsistent with the event-time display snapshot. The plan needs a defined fallback for that case.

The recommended delivery remains **one bounded PR-01**, followed by the feature-owned AC-001 recording gate.

## Assumptions

### Verified

* Every tap-accepted event carries an immutable event-time snapshot before nonblocking enqueue.
* The worker is single-threaded and processes the queue in FIFO order.
* Key-down display selection depends on resolved focused-element/window geometry and falls back to the main display.
* Only two frames per display are retained by the broker.
* The queue can be as small as four jobs and fail-stops rather than blocking or dropping silently.
* Current orderly stop halts streams before worker drain.
* The stored schema and screenshot triple paths are unchanged by this feature.

### Inferred

**Streams must remain live while the worker drains after tap shutdown.** Otherwise recently accepted key-downs can only fall back. This inference would be invalidated by an explicit product decision that orderly stop intentionally cancels post-event waiting, or by a platform guarantee that the relevant frame is always delivered before `stop()` begins; neither appears in the checkpoint.

**A geometry-changed post frame should be rejected in favor of the pinned pre-event frame.** This is the narrowest safe behavior because packet assembly mixes event-snapshot display geometry with selected-frame geometry. It would be invalidated by a coherent cross-generation crop rule or an accepted requirement to capture through display topology changes.

**“First buffered frame” must operationally mean the oldest eligible frame still retained.** It would be invalidated by expanding retained depth or registering an event-specific lease when a future frame is published, both currently non-goals.

**A polling implementation is sufficient if the entire wait runtime is injectable.** This would be invalidated by measured broker-lock contention or unacceptable detection latency. No evidence currently requires a condition-variable refactor.

**One implementation PR remains the smallest cohesive unit.** This would be invalidated if display-generation semantics are expanded into a cross-generation capture capability or if queue/retention policy is reopened.

### Unknown

* The actual runtime queue capacity on the user’s active display configuration.
* Typical and worst-case AX-resolution plus PNG-encoding latency in the signed build.
* Whether the first SCStream frame after each native text-field key-down consistently includes the character; AC-001 exists to determine this.
* Whether a display reconfiguration can occur in the 250 ms selection window in realistic use and what outcome the product expects.
* Whether stopping immediately after the final key currently reproduces a missed-character case.
* The actual maximum queue depth during the required `hello` recording.

## Architecture

### Owning control flow

```text
CGEventTap callback
  ├─ copies event facts and host-clock timestamp
  ├─ pins existing pre-event FrameSnapshot
  └─ try_send(CaptureJob)                         no wait, no AX, no blocking send
          ↓
single capture worker
  ├─ resolves click or key-down metadata
  ├─ selects display using existing DEC-008/DEC-011 rules
  ├─ obtains pinned frame for that display
  ├─ click: uses pinned frame immediately
  └─ key-down:
       query/wait for oldest retained frame in (event_ts, deadline_ts]
       otherwise use pinned frame
          ↓
packet assembly
  ├─ cuts full/window/element crops from one selected FrameData
  ├─ encodes one screenshot triple
  └─ computes saturating frame age
          ↓
PacketEmitter → recording coordinator
  └─ commits PNGs + events.jsonl before emitting the live step
```

This keeps all accepted ownership boundaries intact. The tap still protects input responsiveness; the worker owns the only wait; packet assembly remains pure; persistence remains downstream.

### Broker selection contract

Add one pure query to `FrameBroker`, but make it a **bounded timestamp-range query**, not merely “first frame after”:

```text
deadline_ts_ns = event_ts_ns.saturating_add(250_000_000)

eligible post frame:
    frame.ts_ns > event_ts_ns
    and frame.ts_ns <= deadline_ts_ns
```

The query should choose the minimum eligible timestamp across the two retained slots. It should not depend solely on `previous` being chronologically older than `newest`, even though normal per-display stream publication is serial. It must query only the already selected display ID.

This yields the required late-worker behavior:

* A job that arrives after its deadline may still use a valid retained frame from within the event’s timing window.
* It performs no sleep.
* A frame timestamped after the deadline is not eligible and cannot suppress the pinned fallback.
* Equality with the event is not post-event.
* Equality with the deadline can be treated as eligible as a deterministic boundary convention.

The current plan’s unbounded `ts_ns > event_ts` query would violate DEC-002 when only a later-than-deadline frame is retained.

Do not modify `eligible()` or `snapshot()`: those retain the current click and fallback behavior.

### Worker wait runtime

The production route should remain a short polling loop around the live broker. It is smaller and less invasive than converting every broker user to a condition-variable wrapper. One worker polling for at most the remaining portion of 250 ms has a tightly bounded cost.

The test seam, however, must inject more than a clock. Conceptually, the worker needs:

* `now_ns()`
* `wait_for(duration)`
* production deadline and poll durations, with test-controlled values

A deterministic test runtime can advance its clock and publish a frame into the real broker during `wait_for()`. This tests the actual worker/broker loop without wall-clock sleeping, scheduler races, or a 250 ms test delay. It also proves the worker does not hold the broker mutex while waiting: the test publication would deadlock otherwise.

Production wiring in macOS `pipeline.rs` supplies `hostclock::host_now_ns` and thread sleep. Keeping this dependency in the macOS composition root preserves cross-platform compilation of the pure worker module. `host_now_ns` itself is macOS-only, while the worker module is built off macOS.

The loop should query before waiting and once at the timeout boundary, handle spurious/test wakeups by looping, and use `saturating_add`/`saturating_sub` for timestamp arithmetic.

### Display selection and selected-frame handoff

Extract the existing key-down/click display selection from `packets.rs::build_packet` into a pure shared function. The worker invokes that function after metadata resolution.

After choosing the display:

1. Retrieve the pinned fallback frame from the job snapshot. Its absence remains the existing fail-stop.
2. For a click, select it directly and never consult the live broker.
3. For a key-down, run the bounded query/wait on the same display ID.
4. If the post frame’s `FrameData.display` geometry differs from the selected event-time display geometry, use the pinned frame rather than mixing generations.

Packet assembly should receive an explicit selected-frame value, ideally a small internal value containing the selected display and `Arc<FrameData>`. This is preferable to cloning or overriding `FrameSnapshot` because the snapshot’s meaning remains “what the tap pinned at event time.” It also gives packet tests an unambiguous frame input and a place to enforce display-ID/geometry compatibility.

All three shots must continue to come from that one `FrameData`; no crop or element-resolution rule changes.

### Shutdown boundary

Revise orderly shutdown to:

```text
stop health monitor
stop and join tap                 closes the final JobSender
drop display reconfiguration observer
join/drain capture worker         streams remain active during bounded waits
stop and join stream manager
close emitter guard
```

This preserves the existing quiescence contract while allowing an already accepted key-down to receive a post-event frame after the user presses Stop. The coordinator already calls `pipeline.stop()` before it sends its own finalization message, so packets emitted during this drain remain ordered ahead of finalization.

Dropping the display observer before worker drain freezes topology changes as much as this architecture permits while leaving existing streams publishing. A stream that has already failed or exited simply yields the normal deadline fallback.

### Saturation boundary

Keep queue capacity and DEC-009 unchanged.

The event-anchored deadline gives a useful bound: a burst does not incur 250 ms per queued key. Once the first job’s absolute deadline has passed, later jobs from the same burst query and proceed without their own full wait.

It does **not** guarantee that waiting cannot cause saturation. With a capacity of four, while one job is already executing and waiting, four more can occupy the channel and the fifth additional event is rejected. The plan and ADR should say “prevents waits from stacking linearly,” not “cannot saturate the queue.”

No queue-capacity increase belongs in PR-01. Queue pressure should remain observable through the existing maximum-depth receipt and through the AC-001 run.

### Persistence and compatibility

There is no migration:

* `CaptureMeta.frame_age_ms` remains `u64`.
* `CapturePacket` and `Event` shapes remain unchanged.
* Existing screenshot filenames and one-triple-per-event persistence remain unchanged.
* The review UI continues reading stored PNGs.
* Historical recordings require no rewrite.

The most accurate comment for both `CaptureMeta` and `CapturePacket` is approximately:

> Nonnegative event-to-selected-frame age in milliseconds, saturating at zero; post-event key-down frames therefore report `0`.

This is more accurate than implying that zero uniquely identifies a post-event frame. Existing code also produces zero for sub-millisecond age, equal timestamps, and its bounded-retention approximation.

## Contract conflicts to surface

### “First buffered frame” versus two-frame retention

The goal and DEC-001 use “first buffered frame after the event,” while AC-002 and the plan use “oldest retained frame.” The latter is what the current broker can implement. AX resolution may take long enough for the true first publication to leave the two-frame buffer.

The specification root should make the ADR wording explicit:

> Select the oldest eligible frame still retained after the event, intended to be the first post-event frame under normal worker latency.

A literal guarantee of the historical first frame would require deeper retention or per-event future leases, contradicting the accepted non-goals.

### Literal click invariant versus existing approximation

AC-002 says a click uses the newest retained frame not later than the event. Existing `RetainedFrames::eligible` selects the oldest retained frame even when both retained frames are later than the event, because the true predecessor has already been lost.

PR-01 should not broaden scope by changing this. The acceptance interpretation should be “click selection remains byte-for-byte unchanged,” including that preexisting bounded-retention approximation. Otherwise AC-002 already demands unrelated click/retention work.

### “No wait-driven saturation” overstatement

The event-anchored deadline limits cumulative waiting but does not prove the queue cannot fill during the first wait. Treat this as rationale correction, not a new product decision.

## Recommendation

Revise the existing PR-01 plan and proceed as **one implementation PR** with these binding architectural corrections:

1. Keep the tap callback and pinned snapshot behavior unchanged.
2. Add a pure broker query for the oldest retained frame in `(event_ts, event_ts + 250 ms]`.
3. Resolve metadata and select the display on the single FIFO worker.
4. Inject a complete wait runtime—clock, wait operation, deadline, and poll interval—for deterministic tests.
5. Pass an explicit selected frame into packet assembly; do not redefine or mutate the pinned snapshot.
6. Use the pinned frame when no in-window frame exists, when the selected display has no live frame, or when post-frame geometry is incompatible with the event snapshot.
7. Keep streams publishing until the worker drains during orderly stop.
8. Preserve queue capacity, fail-stop policy, schema, triples, crops, and UI.
9. Expand the automated matrix before treating AC-002 as covered.
10. Land the ADR, README, and accurate doc comments in the same PR, then block merge on the signed-head AC-001 run.

Rejected alternatives:

* **Waiting in the tap:** violates DEC-009 and risks tap disablement.
* **Enqueuing from the stream sink:** loses structural event ordering and complicates clicks interleaved with keys.
* **Parallel per-event waiters/workers:** requires a reorder buffer and expands concurrency substantially.
* **Increasing retained depth or queue capacity:** masks rather than implements the bounded policy and violates explicit non-goals.
* **Capturing both frames or changing schema:** rejected product scope.
* **A broad condition-variable broker refactor:** technically viable, but wider than necessary; bounded polling with an injectable wait runtime is the smaller architecture for this checkpoint.

The consequential unresolved question for the specification root is **display reconfiguration during the key-down timing window**. The recommended engineering default is pinned pre-event fallback whenever the later frame’s geometry differs. Requiring post-event capture across display-generation changes would be a broader product and architecture decision, not an implementation detail for this slice.
