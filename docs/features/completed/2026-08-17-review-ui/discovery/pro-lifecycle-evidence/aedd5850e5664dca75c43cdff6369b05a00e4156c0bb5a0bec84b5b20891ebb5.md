# 2026-08-17-review-ui — primary research and candidate plan

All mandated paths were available from commit `1b659697b3bf5e7fb2b4bf909d377392e162b0f3`. No local-only evidence was supplied or used.

The accepted three-PR sequence is viable, but the current plans need two material corrections before implementation:

1. **Manifest mutations need an explicit serialization and active-recording guard.** Atomic file replacement prevents torn manifests, but it does not prevent two concurrent load–mutate–save operations from losing each other’s changes.
2. **A truthful production UI-proof route must be established before PR-01 can claim AC-002.** Vitest component tests are necessary but do not meet the repository’s UI-verification contract.

There are also two specification-level conflicts the root should not silently resolve:

* The current worker persists parsed steps only during stop/fail finalization, while DEC-005 says a crash before Save leaves nothing lost. Raw events and screenshots survive; reviewable manifest steps do not necessarily survive a crash during active recording.
* The accepted documents do not define duration calculation, landing-thumbnail selection, or how much variant-D detail must be populated during live recording.

## Assumptions

### Verified

* The persisted schema can support the entire accepted review/edit flow without a version bump.
* Workflow IDs and folders remain stable when the user renames a workflow.
* Step deletion changes only `Manifest.steps`; events and screenshots remain until whole-workflow deletion.
* Draft state exists only in the active frontend session after a successful stop/fail finalization.
* The backend permits only one recording at a time.
* Channel delivery is best-effort, while filesystem persistence is authoritative.
* There is currently no frontend component-test harness.
* The inspected checkpoint does not establish a repository-native desktop UI adapter capable of producing the required typed UI proof.

### Inferred

**Duration should be the span between the first and last complete event timestamps, with zero for fewer than two events.** This preserves recording duration when a step is deleted because its events remain. It would be invalidated by prototype or decision evidence defining duration as `created_at → last event`, stop time, or selected-step span.

**A single coordinator-owned manifest-mutation mutex is sufficient for this local single-user application.** It serializes short load–mutate–save operations and finalization without introducing a lock registry. It would be invalidated by measured UI latency or a requirement for parallel edits across multiple workflows.

**A failed recording should enter draft review with an error banner when its manifest finalization succeeded.** This follows the existing guarantee that committed data is preserved. It would be invalidated by a product decision requiring failed sessions to return directly to the landing page or remain non-editable.

**The frontend does not need a routing package.** An in-memory discriminated view state is enough for landing, saved detail, recording, and draft review, and it preserves draft-session identity. It would be invalidated by deep-linking, browser-history, multi-window, or restorable navigation requirements.

**The safest screenshot transport is a backend-owned, allowlisted binary read rather than a broad asset-protocol scope.** This is based on the current null CSP, the sensitivity of `events.jsonl`, and the requirement for a scoped display path. It would be invalidated by verified Tauri configuration that can narrowly expose only canonical PNG paths and by evidence that IPC copying is unacceptable for the expected image sizes.

**The first referenced event is the detail event for today’s one-event-per-step parser.** It would be invalidated when text grouping lands or if the accepted prototype defines a different event-selection control.

### Unknown

These require root resolution or additional evidence before their owning slice:

1. **Landing duration semantics** and invalid/missing-timestamp fallback.
2. **Landing thumbnail selection:** first or last step, and full/window/element variant.
3. **Landing ordering:** preserve current ID-ascending order or show newest first.
4. **Live recording content:** whether rows need only the streamed `Step`, or also event time, metadata, and the screenshot triple.
5. **Rename validation:** trimming, blank-name rejection, maximum length, and whether Save can retain the unchanged timestamp default.
6. **Active-recording crash semantics:** whether “nothing lost” means raw events/screenshots or fully reconstructable review steps.
7. **Responsive target:** whether variant D must fit the current 800×600 window or the product window may become larger.
8. **Truthful UI adapter:** the exact installed capability and production-data setup for intermediate and final proof.
9. **Deletion primitive:** whether the standard-library removal available to this toolchain demonstrably satisfies the ADR’s externally substituted-target requirement on macOS.
10. **Damaged workflow summaries:** whether a valid manifest with a missing/corrupt event log remains visible with placeholders or is omitted.
11. **Failed-recording UX** after a `LiveEnvelope::Failed`.

## Architecture

### Owning seams

```text
React product shell
  ├─ typed Tauri client
  ├─ app/view reducer
  ├─ per-entity autosave queues
  └─ screenshot blob cache
          │
          ▼
Thin Tauri commands
          │
          ▼
RecordingCoordinator
  ├─ recording phase/state machine
  ├─ active-workflow mutation policy
  ├─ serialized manifest mutation/finalization
  └─ platform reveal orchestration
          │
          ▼
WorkflowStore
  ├─ create / append event / load / save manifest / list
  ├─ additive summary calculation
  ├─ canonical screenshot read
  ├─ validated workflow-path resolution
  └─ validated folder removal
          │
          ▼
schema-v1 workflow folders
  ├─ workflow.json
  ├─ events.jsonl
  └─ shots/*.png
```

`commands/mod.rs` should continue to translate IPC arguments and errors only. `RecordingCoordinator` should remain the application-service boundary because it already owns recording phase and the shared store. `WorkflowStore` should remain the sole filesystem boundary.

### Transient data contracts

Keep `Event`, `Step`, `Manifest`, and `ShotPaths` unchanged. Add transient DTOs outside `schema.rs`:

* An extended `WorkflowSummary` with:

  * `step_count`
  * numeric `duration_ms`, preferably optional for damaged/empty data
  * an optional opaque thumbnail reference rather than an absolute path
* A `StepPatch` whose only optional fields are title, description, and classification.
* An allowlisted screenshot variant enum: full, window, or element.
* A screenshot reference containing only the identifiers necessary for the backend to reconstruct the canonical shot path.

For valid workflows, `step_count` should come from `manifest.steps.len()`, not event count. This preserves the step/event distinction when grouping eventually lands. Duration may inspect events, but summary calculation must not turn a damaged event log into disappearance of an otherwise readable manifest without an explicit decision.

### Manifest mutation and concurrency boundary

Atomic replacement solves torn writes, not lost updates. Two autosaves can currently perform:

1. both load manifest version A;
2. one patches title and writes B;
3. another patches description on A and writes C;
4. C silently loses the title change.

The candidate correction is:

* Add a coordinator-owned `Arc<Mutex<()>>` covering all manifest load–mutate–save operations.
* Pass the same lock into the recording worker and take it around final `save_manifest`.
* Do not hold the recording `Phase` mutex while performing filesystem I/O.
* Preserve the active workflow ID in `Recording`, `Stopping`, and worker-owned failure/finalization phases.
* Before `update_step`, `delete_step`, `rename_workflow`, or `delete_workflow`, reject the operation when the target is the active/finalizing workflow.
* Allow mutation of an unrelated saved workflow while another workflow records.
* Keep screenshot reads and ordinary list/detail reads outside the manifest-write lock.

This prevents edit/edit lost updates and stop/edit overwrite races without serializing screenshot capture or event appends. The current coordinator tests already establish strong start/stop race coverage; the new mutation policy should be tested at the same service boundary.

### Store additions

Additive `WorkflowStore` behavior should cover:

* Summary calculation from stored data.
* Canonical screenshot reading.
* Validated path resolution for Reveal.
* Idempotent workflow-folder removal.

The screenshot read must accept identifiers and an allowlisted variant, derive the canonical filename, validate the workflow and event IDs, reject symlinks, and return only PNG bytes. It should never accept an arbitrary frontend-supplied absolute or relative filesystem path.

Removal must:

* validate the workflow ID;
* treat a missing root or target folder as success;
* reject a target that is a symlink or non-directory;
* remain confined to the configured root;
* prevent or detect target substitution between validation and removal;
* remove the entire folder and write no tombstone or replacement artifact.

A test that only starts with a pre-existing symlink is insufficient for the ADR’s “externally substituted target” wording. The implementation needs either a deterministic substitution hook/test or a filesystem primitive whose race-safety is established for the supported macOS/toolchain.

### Screenshot display path

Prefer a backend-scoped binary read over enabling the asset protocol for the workflow root.

A broad scope such as `workflows/**` would potentially expose `events.jsonl`, including recorded keystrokes, alongside screenshots. The current configuration also has no CSP, so minimizing directly addressable local files is prudent.

On the frontend:

* Convert returned image bytes to blob URLs.
* Cache them by workflow ID, event ID, and variant.
* Revoke URLs when the workflow/view cache is discarded.
* Show a labeled placeholder on a missing or unreadable image rather than collapsing the triple layout.
* Do not persist blob URLs in state beyond the active frontend session.

The exact binary-response mechanism is an implementation choice. The required architectural property is that only canonical PNGs are readable through the endpoint.

### Reveal

Reveal should remain a backend command:

1. resolve and validate the workflow directory through the store;
2. invoke the macOS reveal/open operation in the backend;
3. return success or a surfaced error.

This avoids adding a frontend shell/filesystem plugin and avoids exposing raw absolute paths. The platform operation should be separated enough to test path validation without opening Finder during unit tests.

### Frontend composition

The current `App.tsx` boolean state should become a discriminated reducer with explicit states such as:

* landing loading/ready;
* starting recording;
* recording;
* stopping;
* draft review;
* saved-workflow detail;
* fatal/recoverable load failure.

No routing dependency is needed for the accepted flow. `App.tsx` can own composition while implementation-specific components, styles, and typed API wrappers are split under `src/`.

A typed frontend client should be the only module importing Tauri `invoke` and `Channel`. Components and reducer tests should use an injected fake client rather than repeatedly mocking Tauri internals.

### Recording control flow

1. From landing, create and retain a channel, assign a new frontend session token, and enter `starting` before invoking `start_recording`.
2. Accept step messages even if they arrive before the start promise resolves.
3. Deduplicate/order live rows by step ID and ignore messages from a stale session token.
4. Once start returns, reconcile its workflow ID with any terminal ID already observed.
5. During recording, render the Stop banner as the **only visible action**. Do not merely disable rename, delete, back, Save, or Discard controls.
6. On first Stop, enter `stopping` and disable repeat stop requests.
7. After successful finalization, load the workflow and enter draft review.
8. Open Save with the loaded manifest name selected.
9. Save calls `rename_workflow` and changes only frontend draft status; Discard calls the same backend deletion primitive used by saved Delete.
10. On channel failure, preserve the workflow ID and committed live rows. The exact destination state remains a product decision.

The channel is terminal-last and best-effort, so the reducer must reconcile both the stop command result and terminal envelope rather than assume a fixed JavaScript callback order.

### Detail view model

Build an event map keyed by `Event.id`. For each manifest step:

* resolve its first current event by `event_ids[0]`;
* derive screenshots from that event;
* derive time, window/app, coordinates, key, and element/source from the event;
* do not pair `steps[index]` with `events[index]`.

Index pairing would become wrong immediately after step deletion because the event remains in the log. It would also fail when grouping eventually produces multiple event IDs.

The triple viewer should maintain a selected primary variant. One image is large; the other two remain visible as labeled swap controls. A missing image should keep its labeled slot.

### Autosave

Use local optimistic state with a serialized queue per step/workflow:

* Title and description may save on a short debounce or blur.
* Classification saves immediately.
* Rename uses the same queue discipline.
* A later user edit must not be cleared by completion of an earlier request.
* Step deletion first marks the step non-editable and prevents queued updates from being sent afterward.
* On backend failure, retain a visible error and reload or revert to authoritative stored state.

Backend serialization remains mandatory even with frontend queues; IPC can still be invoked by stale UI code, future windows, or tests.

### Persistence and migration obligations

No schema migration is needed:

* Draft state remains frontend-session state.
* Rename changes `Manifest.name`.
* Step edits change existing `Step` fields.
* Step deletion removes an existing manifest entry.
* Summary fields are computed responses, not persisted fields.
* Screenshot references are transport/view data.
* Whole-workflow deletion removes existing files rather than writing a state marker.

The schema-v1 golden tests should remain unchanged and continue to pass.

The bundle should preserve these compatibility properties:

* Existing workflow folders remain readable.
* Unknown additive JSON fields remain tolerated on read.
* Renaming never invalidates workflow IDs or screenshot references.
* Step deletion retains events and screenshots.
* Listing one damaged folder does not hide unrelated workflows.
* No restore or forensic-erasure claim is introduced.

### Active-recording crash conflict

The present worker appends raw events and screenshots continuously but writes parsed steps only during finalization. A process crash during active recording can therefore leave:

* a valid folder;
* an empty or stale manifest step list;
* committed events and screenshots.

Because re-parse is explicitly out of scope, the review UI cannot reconstruct those missing steps without changing an accepted boundary.

The root should choose one interpretation before delivery:

* **Narrow interpretation:** “nothing lost” means raw captured facts and images survive; the current feature does not guarantee reviewable steps after a crash during active capture.
* **Stronger interpretation:** reviewable steps must survive such a crash, requiring either incremental manifest persistence or an accepted re-parse/recovery path.

The stronger interpretation is not a silent implementation detail; it changes capture/finalization behavior and scope.

### UI proof architecture

Vitest/Testing Library prove component and interaction logic with a fake client. They do not satisfy the repository’s project-UI proof contract, which requires unchanged production composition and a typed artifact.

Before PR-01 can close AC-002, the root must identify a route that can:

* launch the exact implementation worktree or committed Tauri head;
* populate or obtain valid production filesystem data at an accepted production-owned seam;
* navigate the real app;
* observe a stable control or displayed value;
* produce the typed `project-ui-proof` artifact;
* keep the live session available for PR-03’s final human decision.

The existing capture gate should remain historical capture evidence, not be relabeled as this bundle’s AC-001. Its instructions target the dev-only UI that PR-01 removes, and its unqualified “AC-001”/“PR-03” naming would be ambiguous in the new bundle.

A new bundle-qualified proof script or receipt path should cover:

1. landing summaries and permission gate;
2. saved detail, triple swap, edits, rename, and step deletion;
3. live recording and Stop-only action;
4. draft badge, Save naming default, and Discard;
5. Reveal before deletion;
6. Cancel-default destructive confirmation mentioning keystroke data;
7. row removal only after backend success;
8. actual folder absence after confirmed deletion.

## Risks and missing evidence

### 1. UI-proof route is not established

The accepted plans state “automated UI proof,” but the inspected checkpoint establishes only a generic receipt validator and component-test setup proposal. The route forbids substituting a mocked browser/component path for production composition. This is a **slice-entry blocker for PR-01 acceptance**, not something to defer until PR-03.

### 2. DEC-005 overstates active-recording crash recovery

Raw capture data is continuously persisted; review steps are not. The root must narrow the wording or accept additional recovery scope. Implementing re-parse would directly conflict with the stated non-goals.

### 3. Current plans omit manifest write races

PR-02’s proposed “load → mutate → save” path is unsafe when autosaves overlap. Atomic rename is not concurrency control. The coordinator lock and active-workflow guard must be explicit plan requirements.

### 4. Hard-delete substitution resistance is not yet proven

Existing confinement helpers are a good base, but validation followed by recursive removal requires a race-safety argument and tests. The ADR’s substituted-target wording should not be weakened to “rejects a symlink that was already present.”

### 5. Summary semantics are underspecified

Duration, thumbnail source, sort order, and damaged-workflow fallbacks influence backend DTOs, tests, and the pinned landing UI. These should be bound before PR-01 implementation.

### 6. Live recording may lack required display data

`LiveEnvelope::Step` has no timestamp, event metadata, or screenshot reference. If recording mode must render the complete variant-D pane rather than only streamed text rows, the accepted backend delta is incomplete. Avoid an O(n²) `get_workflow` reload after every event; resolve the product requirement first.

### 7. The current 800×600 window may not support the selected composition

An always-visible large image, two thumbnails, metadata, editor fields, and compact list may require a larger initial window or carefully proven responsive behavior. This belongs in PR-01’s production UI proof.

### 8. Existing capture gate naming is ambiguous

`dev/proven-gate/script.md` calls itself AC-001 and refers to final PR-03, but those identifiers now also exist in this bundle with different meanings. New evidence should always bind the work bundle and slice, and the review-UI proof should have a bundle-qualified path.

### 9. PR-03 remains the highest-risk slice

Record-channel state, draft lifecycle, irreversible deletion, final UI design, real TCC permissions, and end-to-end proof all converge there. Keeping it as one PR is acceptable only because the three-PR serial sequence is already accepted; its internal checkpoints should be treated as mandatory review stops.

## Recommendation

Adopt the three accepted serial PRs with these amendments:

1. **PR-01 establishes the secure read/list/navigation foundation and the truthful UI-proof route.**
2. **PR-02 introduces a coordinator-owned mutation boundary before any autosaving detail UI ships.**
3. **PR-03 reuses those foundations for record/draft state and one root-confined removal primitive, then runs a new bundle-specific signed-app final gate.**

Before PR-01 implementation, the spec-work root should bind these consequential questions:

* duration calculation;
* thumbnail event and shot variant;
* landing order;
* valid-manifest/damaged-event fallback;
* current-window versus enlarged-window target;
* required live-recording row/detail content;
* blank-name behavior;
* failed-recording destination;
* active-recording crash interpretation;
* exact production UI adapter.

Rejected alternatives:

* **Broad asset-protocol access to the workflow root:** too much exposure for raw keystroke logs and unnecessary with a narrow screenshot resolver.
* **Frontend `get_workflow` once per landing row:** repeats event-log work and violates the accepted summary ownership.
* **Fire-and-forget autosaves:** creates lost-update and stale-response races.
* **Persisted draft flag or schema v2:** conflicts with DEC-005 and adds no required behavior.
* **Optimistically hiding a deleted workflow before backend success:** conflicts with AC-005 and the hard-delete ADR.
* **All backend work in PR-01:** not a vertical slice and delays observable product proof.
* **A fourth PR solely for workflow deletion:** architecturally cleaner than the current PR-03 load, but contrary to the accepted three-slice delivery contract unless the spec-work root changes that decision.
* **Re-parsing event logs on startup to recover missing active-session steps:** directly crosses the feature’s non-goal boundary and requires semantic authority outside this planning pass.

The recommended plan preserves schema v1 and the existing store/coordinator composition, makes concurrency and deletion correctness explicit, and leaves the unresolved product semantics with the spec-work root rather than embedding them as implementation guesses.
